[experimental] `astryx experimental export`: an https image the page shows only later (after a click, in the next view) is carried too, when the page's own code writes its address whole. That means an address whose path ends in an image extension, the value of a JSX `src`, `srcSet` or `poster`, or the value of a property or attribute one of whose words names an image (`avatarUrl`, `cover_image`; not `logoutUrl`). It is fetched with the same rules and limits as an image in the first paint, and listed in `remoteImages`. The page's script keeps every address as the page wrote it, so a link, a text, a comparison and the URL API read the page's own address. Where the browser takes an image's address (an image's `src` or `srcset`, a picture source's `srcset`, a video's `poster`, an image input's `src`, an SVG image's `href`, or a CSS `url()` in a style the script sets), the file gives it the carried data instead, so the image shows offline. An address the code gives a fragment gets the carried image too; one it gives another query (`${hero}?w=640`, or the URL API's `searchParams`) can name another image, so the file asks the network for it. A link's address written in `href`, directly or through a variable that only links read, is never fetched, even when it names an image file. An address that counts only by an image word in a name around it (`imageUploadUrl`) can be an API's: when its answer is another type (an API's JSON, a page), `remoteImages.failed` lists it with why, with no warning. Any other address the script draws later warns when its fetch fails, as in the first paint. No other address is fetched. An image address the code builds from parts right where an image goes (a template or `+` chain that starts with `https://`, in a `src`, `srcSet`, `poster` or image-named property) cannot be carried: a `remote-asset` warning names it, its file and its line. An address built any other way is neither carried nor warned.
