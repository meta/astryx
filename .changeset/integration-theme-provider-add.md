[feat] `astryx theme add`, on the first add, when an installed package names the provider that wires its themes, says so: "This app may already get its theme from <Provider> (from <module>, declared by <package>)", with the props it takes the theme and mode through. When that one provider takes the theme (its manifest's `themeProvider` names `themeProp`), every receipt that shows wiring shows that provider in place of a Theme wrap: the first add passes the generated module's theme to it (`<Provider theme={themes[defaultThemeSlug]}>`, plus `<modeProp>={themeModes[defaultThemeSlug]}` for a theme with one color mode when it names `modeProp`), a later add that first lists `themeModes` passes the mode to it when the manifest names `modeProp`, and `theme remove` of the last theme undoes those props and keeps the provider. With no `themeProp`, or two such providers, the first add names each provider and its trade-off ("Replacing <Provider> applies this theme everywhere but also drops anything else it sets up; a Theme inside it themes only what it wraps.") above the Theme wiring. No receipt reads app source. The JSON carries it as `appProvider`: each provider as `{export, from}` (with `themeProp` and `modeProp`), `wire`, and `themeProp` and `line` when the provider form applies. An integration manifest's `themeProvider` takes an optional `themeProp` and, beside it, an optional `modeProp`. `themeProvider` is a hint and never stops a manifest loading: a part this CLI cannot use (an export that is no component name, a prop that names no prop, a `modeProp` with no `themeProp`) is dropped with an `ignored_manifest_field` warning.
