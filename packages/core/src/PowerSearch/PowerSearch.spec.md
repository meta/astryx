# PowerSearch component contract

## Intent

PowerSearch provides structured filtering through field, operator, and value
selection. Its editor popover keeps the active editing task readable on both narrow
and wide search bars. When the editor can follow the PowerSearch width, it stays
aligned to that outer surface. When the 720 CSS px readability cap makes the editor
narrower, it stays near the stable control that opened it instead of stretching
across the page or depending on input modality.

PowerSearch also offers an experimental touch presentation (DEC-3): the whole
field becomes one trigger showing display-only filter tokens, and the filter
work moves into a flow of tall modal bottom sheets — Filters, Add filter, and a
value step — that reads on a compact touch screen without a software keyboard
covering the editor. Omitting the option keeps the tokenizer and editor popover
on every device.

Where the shipped PowerSearch does not yet meet a requirement, the row carries a
present-tense implementation gap note.

## Compatibility and migration

- Released default preserved: `no` for editor popovers anchored to a PowerSearch
  wider than 720 CSS px; other widths preserve their current sizing behavior.
- Compatibility class (DEC-1, DEC-2): intentional default layout and placement
  change with no public API change. DEC-3 adds the `experimental.presentation`
  option, outside the stable compatibility promise, as the Experimental surface
  bullet states.
- Controlled/uncontrolled behavior: unchanged.
- Migration decisions: `component:PowerSearch/DEC-1` and
  `component:PowerSearch/DEC-2`.
- Experimental surface (DEC-3): the touch sheet presentation is the
  `presentation` option inside the optional `experimental` prop object, outside
  the stable compatibility promise (`spec:AST-017/FR21`). Omitting `experimental`,
  or omitting `presentation` inside it, keeps the tokenizer field and its editor
  popover on every device. Changes to the option ship as `[experimental]` patch
  releases (`spec:AST-017/FR22`). While the option is experimental the sheet
  presentation adds no theming target (`spec:AST-017/FR27`).
- One stable fix alongside DEC-3, outside the experimental exception
  (`spec:AST-017/FR22`): the result count is not announced on mount under
  StrictMode (FR19). It qualifies as a `[fix]` under `spec:AST-017/FR5`: it
  restores the documented contract (only a change after mount is spoken), no
  `onChange` value, prop, or rendered text changes, and no valid consumer
  must change. It ships as a `[fix]` patch release of its own.

Consumer migration instructions belong in consumer docs and release notes.

## Ownership boundary

**Owns**

- The readable width range of the filter-editor popover.
- Identifying the stable control that opened the editor: the inner typeahead input
  for the add path, or the actual activated token/control for the edit path.
- Choosing which outer PowerSearch edge a width-capped editor aligns to from that
  opening control's geometry.
- Preserving the editing flow, content, and focus behavior while the editor's width
  and horizontal alignment change.
- The touch sheet presentation: its trigger, the Filters, Add filter, and value
  sheets, the order of steps, which control receives focus after each step,
  the staging of a value until the step confirms it, the `onChange` metadata of
  each commit, and which PowerSearch props the sheets honor.

**Does not own / non-goals**

- Main field/search-menu width — the existing `menuWidth` consumer surface is an
  exact pixel width forwarded to Tokenizer's main field menu, not a maximum and not
  an editor width control.
- General anchor positioning, viewport collision handling, top-layer hosting, or
  dismissal — owned by `architecture:layer-runtime`.
- Operator- and value-menu sizing inside the editor.
- A public prop for overriding editor width or placement.
- Pointer-coordinate placement, pointer-versus-keyboard branches, continuous
  pointer tracking, or an always-on geometry observer.
- The compact-touch resolution rule behind `adaptive`. PowerSearch resolves
  `adaptive` with the same shared policy the selection controls use
  (`component:Selector/FR4`); it adds no query of its own.
- The sheets' dialog, the one scrim of the stack of open modal sheets, gestures,
  snap behavior, keyboard accommodation, which sheet is on top and so takes a
  dismissal, and the handoff between steps — owned by `component:BottomSheet`
  (its sheet stack and same-update replace) and `family:overlay-dismissal`;
  `component:BottomSheetSwitcher`, the deprecated predecessor of standalone
  step sheets (its DEP-0015), only while the shipped flow still hosts its
  steps in it.
- The list-value sheet a `string_list` or `entity_list` value opens inside the
  value step — owned by `component:Tokenizer` (its DEC-3 sheet presentation).

## Public concepts

One public concept is introduced, as an experimental surface: the optional
`experimental` prop object and its `presentation` option, `'popover' |
'bottom-sheet' | 'adaptive'` (DEC-3). The option type is inlined on the prop;
no experimental hook or type is exported. Declarations carry `@experimental`
and consumer docs carry `stability: 'experimental'` metadata.

The inclusive 400–720 CSS px range and conditional alignment of the editor
popover are internal PowerSearch readability policy, not callsite options.
Existing `menuWidth` remains an exact pixel width for only the main field/search
menu of the `popover` presentation.

In the sheet presentation the props that describe the tokenizer's typeahead
popover have no surface to act on: `menuWidth` and `tokenOverflowBehavior`.
Passing either while a field resolves to `bottom-sheet` warns once in
development; neither is silently dropped. `ref` reaches the root element in
both presentations, the element this record promises
(`architecture:public-component-api/INV8`); `xstyle`, `className`, and `style`
reach the field container in both. `data-testid` reaches the field's primary
control: in the `popover` presentation the combobox input, where it is today,
and in the sheet presentation the trigger button. `handleRef.focusTypeahead()` and
`blurTypeahead()` act on the trigger. Every other prop keeps its meaning: `label` names the
trigger and `placeholder` is its empty text and the content-search placeholder;
`isDisabled`, `disabledMessage`, `startIcon`, `endContent`, `resultCount`,
`status`, `statusVariant`, `size`, `hasAutoFocus`, `onFocus`, and `onBlur`
apply to the trigger as FR11 states; `hasClear` governs Clear all (FR12);
`isReadOnly` governs the rows, Add filter, and the value step (FR12, FR13,
FR15); `maxSearchResults` and `maxOperatorMenuItems` apply to the Add filter
and value steps (FR13, FR17); `popoverSaveButtonLabel` and `components` apply
to the value step and the trigger (FR11, FR14); `maxTokenLength` applies to the
trigger's tokens as to the popover's (FR11). `timezoneID` changes nothing in
the sheet presentation: the trigger's tokens, the Filters rows, the custom
Editor's props, and the date editors read and format exactly as the popover
presentation's do (FR11, FR12, FR14, FR17).

### Allowed variation

- **AV1 — Viewport clamping.** The layer runtime may shift or shrink the editor
  when the preferred width or edge alignment would cross its viewport safe area.
- **AV2 — Writing direction.** Implementations may express the selected physical
  edge through logical alignment values as long as the rendered edge is correct in
  both LTR and RTL.
- **AV3 — Submenus.** Operator and value menus may retain their own width and
  collision behavior; this contract applies only to the filter-editor popover.
- **AV4 — Internal representation.** The shared opening-control descriptor may use
  refs, elements, or an equivalent package-internal value. Its observable geometry,
  lifetime, and precedence must satisfy FR3–FR9.
- **AV5 — Sheet flow composition.** The sheet presentation hosts its steps as
  standalone BottomSheets driven by one step state — a step that closes in the
  update another opens is replaced by it in place (`component:BottomSheet`
  FR10), the pattern `component:BottomSheetSwitcher` DEP-0015 names as the
  deprecated switcher's replacement — or, until that replace is shipped, in a
  BottomSheetSwitcher; it may compose List, RadioList, TextInput, Button, Heading, and Text in any
  internal structure, and may load the whole surface on demand, provided
  FR10–FR21, AR4–AR6, and PR5 hold and the composition stays within
  `architecture:component-style-authoring/INV7`: one presentation mounted per
  open layer, no content mounted twice, and the open flow under a coarse
  pointer with at most as many elements as the popover presentation's open
  editor under a fine pointer — measured on the Experimental Adaptive story at
  390×844 as `document.body.querySelectorAll('*').length`: 166 at rest and 334
  with the editor popover open under a fine pointer; 123 at rest, 296 with the
  Filters sheet open, 296 with the Add filter sheet open, 318 with the value
  step open on a choice-row value, 328 on a list value, and 401 with the
  Tokenizer's list-value sheet open above the step under a coarse pointer —
  the last by the owner exception DEC-3 records. The Tokenizer's list-value sheet opens as a
  standalone sheet above the step in either composition.
- **AV6 — Sheet layout.** Sheet padding, the field-list search threshold's
  visual placement, row density, and the footer's button widths may vary; the
  44px minimum size of every sheet action and the edge-to-edge rows on the
  body's inset are the constants.

### Transformation and precedence order

- **ORD1 — Width.** Resolve outer PowerSearch width → apply the 400 px readable
  floor → apply the 720 px readable ceiling → yield to available viewport width.
- **ORD2 — Opening control.** Resolve the stable inner input or activated
  token/control for the current open.
- **ORD3 — Horizontal alignment.** If the ceiling did not narrow the editor, use
  outer logical start. Otherwise compare the opening control's physical edge gaps
  inside the outer PowerSearch → choose the nearer outer edge → use outer logical
  start on a tie.
- **ORD4 — Collision.** Let the layer runtime apply viewport collision handling
  after preferred width and edge selection.

### Performance and resources

- **PR1 — One batched open-time read.** PowerSearch MUST read the outer PowerSearch
  and opening-control geometry together once in response to open intent, never
  during React render.
- **PR2 — Hidden commit before show.** Placement state MUST commit while the editor
  popover is hidden, and the popover MUST show on the next animation frame. Real
  Chromium verification MUST prove there is no first-frame flash at a default or
  stale position.
- **PR3 — Latch, do not track.** The resolved opening control and preferred edge
  MUST remain latched until close. The implementation MUST NOT install continuous
  pointer tracking or an always-on geometry observer.
- **PR4 — CSS owns responsive geometry.** CSS anchor sizing and the layer runtime
  MUST own the 400–720 width policy and collision behavior. JavaScript may select
  the per-open anchor/alignment descriptor but MUST NOT continuously calculate
  popup width or collision offsets.
- **PR5 — The sheet surface is opt-in cost.** A field in the `popover`
  presentation does not load the sheet flow's code; the flow's chunk loads on
  demand while a field resolves to `bottom-sheet`, so the first press does not
  wait for the network, and renders nothing on the server or during the
  hydrating render. At rest the field renders none of the flow: its three
  dialogs, rows, search field and editors are mounted only from the press until
  the exit has completed and focus is back on the trigger
  (`architecture:component-style-authoring/INV7`); the trigger, its end lane
  (the result count, `endContent`) and the field chrome of FR11 render as the
  field does. Implementation gap: no sheet surface exists.

## Accessibility contract

- **AR1 — Modality equivalence.** Pointer, keyboard, and programmatic activation of
  the same control MUST resolve the same preferred edge. Keyboard users retain the
  current field selection, editor focus, traversal, apply/cancel, Escape, and
  focus-return behavior.
- **AR2 — Semantic stability.** Width and placement MUST NOT change the current
  combobox, listbox, option, menu, or editor semantics and accessible names.
- **AR3 — Visible content.** Viewport clamping MUST keep all editor controls
  horizontally reachable without requiring page-level horizontal scrolling.
- **AR4 — Trigger semantics.** In the sheet presentation the trigger is a button
  named by the field label plus its visible text, with `aria-haspopup="dialog"`
  and `aria-expanded`; `status.message` and `disabledMessage` describe it; a
  disabled trigger uses `aria-disabled` and keeps its focus order; an
  interactive `endContent` is a sibling of the trigger with its own name and
  tab stop, never a descendant of it. Implementation
  gap: no trigger exists.
- **AR5 — Sheet semantics.** Each step is a modal dialog named by its title
  ("Filters", "Add filter", the value step's title); the Filters rows, field rows, and
  suggestion rows are buttons named by their visible text; a choice row is a
  `radio` (single choice) or a `checkbox` (`enum_list`) named by its visible
  text and checked through `aria-checked`, in a `radiogroup` or `group` named
  by the field label — the radio group one tab stop with arrow-key movement
  that checks and Space or Enter checking the focused row, the checkbox rows
  one tab stop each toggled by Space or Enter (FR17, `spec:AST-020/FR15`);
  the operator step is a radio group named "Operator" of native radio inputs,
  which the arrow keys move and check and Space checks; the content search is a searchbox named "Search"
  controlling the suggestion list; the field-list search is a textbox named
  "Search filters"; every sheet action is at least 44px tall. Implementation gap:
  no sheets exist.
- **AR6 — Announcements and focus.** While a sheet is open, every announcement
  the flow makes — `Added {label}` for a committed suggestion, `Removed {label}`
  for a filter removed from the value step (the label is the Filters row's
  text — the same "{label} {value}" catalog message the row renders, its
  summaries and relative-date values resolved from the catalog as FR12
  states; the popover presentation's removal is the Tokenizer's `tokenRemoved`
  with the filter's `formatFilterValue` label, "{field}: {operator} {value}"
  — not the token's text: `1500` with `units: 'ms'` shows "1500" on the token
  and is announced "1,500 ms" — and the sheet's is the Filters row's text, so
  the two readings differ wherever FR12's row and `formatFilterValue` differ),
  the result count of
  FR19, the Add filter sheet's empty-result messages ("No results found",
  "No filters match your search") and the value step's "This filter is no
  longer available" (FR14), which are plain rendered text, not an EmptyState,
  read from the rendered element and spoken once per query that matches
  nothing, or once per opened filter, by the shared own-content module
  (`architecture:react-component-runtime/INV10`), so nothing speaks them a
  second time — is delivered by a persistent polite live region inside the
  open sheet: an element that stays mounted while
  its text changes and never mounts already holding the text to announce
  (`spec:AST-086/FR3`), that delivers the content added inside it at its own
  polite urgency (`spec:AST-086/FR4`), and that is the route an owner inside an
  open native modal takes (`spec:AST-086/FR14`), so the announcement reaches
  assistive technology behind the native modal dialog where a channel outside
  it does not. Clear all closes the flow and announces "All filters
  removed" once the sheet's dialog has finished its exit and focus is back on
  the trigger — not before, since the closing dialog stays modal through its
  exit and hides both its own region and the channel outside it — through the
  route `spec:AST-086/FR14` names for the field's position then: the modal
  that holds the field, or the shared channel when none does. A result count that changes while the flow is
  closing (Clear all's commit) waits the same way and the two are spoken as one
  catalog message, "All filters removed. {result count}", so a locale orders
  and punctuates the pair; while the flow is closed the result count takes the
  same FR14 route (FR19). Focus moves as FR16 states and returns to the
  trigger after the flow closes. Implementation gap: no flow exists.

## Decision log

### DEC-1 — PowerSearch owns one internal readable editor width

**Reference:** `component:PowerSearch/DEC-1`
**Decider:** `cixzhang`, 2026-08-31

A very wide editor makes a small field/operator/value task harder to scan, while a
callsite width prop would turn readability policy into permanent public API and
produce inconsistent products. PowerSearch therefore owns one internal preferred
range: outer PowerSearch width clamped to 400–720 CSS px, then constrained by the
viewport. This rule does not change Tokenizer's main-menu sizing or PowerSearch's
existing exact-pixel `menuWidth` surface.

Rejected: a public editor width/max-width prop, applying the 720 cap to Tokenizer's
main menu, or treating `menuWidth` as an editor width.

### DEC-2 — Only a capped editor follows the stable opening control

**Reference:** `component:PowerSearch/DEC-2`
**Decider:** `cixzhang`, 2026-08-31

A full-width or floor-expanded editor remains aligned to the outer PowerSearch.
Only when the 720 px ceiling makes the editor narrower does PowerSearch use the
stable opening control to choose the nearer outer edge. The add path uses the
inner typeahead input; the edit path uses the actual activated token/control. The
control's geometry produces the same result for pointer, keyboard, and programmatic
activation, and the result is latched until close.

Rejected: pointer-coordinate placement, pointer-versus-keyboard branches, always
using one edge, anchoring every width to the inner control, continuous tracking,
render-time geometry reads, and showing before hidden placement state commits.

### DEC-3 — The touch sheet presentation is an experimental option

**Reference:** `component:PowerSearch/DEC-3`
**Decider:** `imdreamrunner`, 2026-10-23

PowerSearch offers its touch surface through the `presentation` option of the
optional `experimental` prop object, with the values `popover`, `bottom-sheet`,
and `adaptive` that the selection controls and Tokenizer use. The option is
marked `@experimental` in declarations and `stability: 'experimental'` in
authored docs, so it may change or be removed in a patch release
(`spec:AST-017/FR21`). Omitting `experimental` keeps the tokenizer field and its
editor popover on every device. `adaptive` resolves through the shared compact
coarse-pointer policy, so a PowerSearch, a Tokenizer, and a Selector on the same
page switch together.

The sheet surface is the Lab touch flow: the whole field is one trigger with
display-only tokens; a Filters sheet lists the filters as rows with Add filter,
Done, and Clear all; Add filter lists the fields, or carries the content search
with inline suggestions; the value step stages field → operator → value and
confirms from its footer, with Remove while editing. Closed vocabularies are
rows; list values edit through the Tokenizer's sheet presentation titled with
the field label; a `nested` value uses the popover presentation's built-in
nested editor; every other value type uses the editor the popover presentation
uses, so a filter reads the same in both presentations of one field. Clear all
keeps the popover presentation's semantics (every filter, `remove` at the last
index). Rejected: switching surfaces automatically on `pointer: coarse` without
an opt-in (changes stable behavior). Rejected: a top-level stable `presentation`
prop before the surface has consumer evidence. Rejected: a separate touch
component chosen by the caller (two components, two draft states, an import swap
per breakpoint). Measured against `architecture:component-style-authoring/INV7` on the
Experimental Adaptive story (390×844, `document.body.querySelectorAll('*')`):
fine pointer 166 at rest and 334 with the editor popover open; coarse pointer
123 at rest, 296 with the Filters sheet open, 296 with the Add filter sheet
open, 318 with the value step open on a choice-row value, 328 with it open on a
list value (its Tokenizer trigger), and 401 with the Tokenizer's list-value
sheet open above the step (FR21) — every single-sheet state stays under the
open popover's 334. The stacked state does not, and exceeds it by more than
the 5-element open-layer allowance (`spec:AST-017/FR60`, `DEC-29`), so it is
this record's owner exception to INV7's layer budget, with its counts: before
the Tokenizer's sheet opens, 328 (the value step open on a list value, the
Tokenizer's trigger inside it); after, 401 — the step's dialog stays mounted
as a covered sheet of the stack (`component:BottomSheet` FR6: receded, blocked,
its state kept so the staged value survives) and the Tokenizer's sheet adds
73 above it, its own dialog with search field, checkbox rows, footer and live
region — a second surface the popover presentation never has, since its list
value edits inline in the one editor popover. Existing elements cannot do the
job: the covered step must stay mounted to keep its staged state and take
focus back when the top sheet closes (FR21), and the top sheet is the
Tokenizer's own surface. The counts are re-measured when either surface
changes. Owner exception to INV7's surface budget, which asks that a
pointer-specific presentation be a change of attributes and styles on the same
elements: under `adaptive` the closed field swaps its elements by pointer — the
tokenizer field with its combobox input and token remove controls for one
trigger button holding display-only tokens (FR11) — because the two surfaces
differ in role (a combobox editing inline against a button opening a modal
flow), and a combobox cannot be restyled into a dialog trigger without lying
about its role. The swap renders fewer elements, not more (123 against 166 at
rest), and happens only on resolution changes (FR10); the Tokenizer's own
`adaptive` trigger records the same exception.
Rejected: sheet-only Clear all semantics that keep read-only
filters (the two presentations of one field would clear differently). Rejected:
sheet-only date editors that read dates in `timezoneID` while the popover's read
them in UTC (one filter would show two days).

## Open questions

- Known gap, pre-existing in the popover presentation, against
  `architecture:internationalization/INV1a`: its token writes the list,
  date-range, and nested summaries ("{n} items", "date range", "{n} filters")
  as English literals, joins the items of a list value with a literal ", "
  where FR12's rows use the locale's list format, and shows a relative-date
  value as the stored key (`3d_ago`), and its relative-date editor writes the
  choice labels ("3 days ago") as English literals. `formatFilterValue` resolves its
  summaries from the catalog but differs from the token in five places: it
  formats a `date_absolute` value with a time of day in `timezoneID` where the
  token shows a date only in the device's zone; it says "{n} entities" for an
  entity list where the token says "{n} items"; it formats an `integer` or
  `float` through the locale's number format and appends the operator's
  `units` where the token prints the raw number; it collapses a list to a
  count when the joined text exceeds the width budget, where the token
  compares the labels' total length, so the two collapse at different
  lengths; and it cuts a single value at a different length and with a
  different mark — the token's budget is `maxTokenLength` less the field and
  operator label lengths, at least 10, with 3 characters of slack and "..."
  (three periods), where `formatFilterValue` cuts at `maxTokenLength` with "…"
  (the ellipsis character) — (both show a relative-date value as stored). The sheet presentation
  resolves all of these from the catalog, or the locale's formats, on its own
  surfaces (FR12, FR20) and shows the popover token as it is on the trigger
  (FR11); changing the
  token's and the editor's own text is a separate stable change for the
  owner.
- Known gap, pre-existing in the popover presentation and inherited by the
  sheet: the date editors store a picked day as UTC midnight, while the
  tokens format `date_absolute` in the device's zone and `formatFilterValue`
  in `timezoneID` or the device's zone, so in a zone offset from UTC a filter
  can read as a neighbouring day on its token or in `formatFilterValue`'s
  output. Changing what the editor stores changes the `unixSeconds` that
  `onChange` reports and how saved filters reopen (`spec:AST-017/FR5`,
  `FR7`), so the fix is a separate stable decision for the owner, not part of
  DEC-3; the sheet matches the popover as it is.
- Known gap against `family:input-fields/FR10`, opened by DEC-3: the sheet
  presentation's trigger composes Field for the box the tokenizer field has,
  so PowerSearch is now a component that composes Field, which FR10 binds
  even outside the family's membership, and this record departs from FR10 in
  two places. Item 1: `ref`, `id`, `data-*`, `aria-*`, `hidden`, `inert`,
  `dir`, and DOM event handlers go to the primary semantic control under
  FR10, while this record keeps `ref` on the root in both presentations (the
  INV8 promise above), routes only `data-testid` to the primary control, and
  forwards no `id`, `aria-*`, other `data-*`, `hidden`, `inert`, `dir`, or
  handler at all — the stable component destructures its props with no rest.
  Items 2–4: PowerSearch's stable props carry root `xstyle`, `className`, and
  `style`, which both presentations apply to the field box — FR10's
  `container*` target — so the styling lands where FR10 puts it, but the
  props type still accepts the root names and offers no `container*` or
  `control*` parts. Moving `ref` or removing the root names is a stable API
  change for existing callers (`spec:AST-017/FR5`), so the conversion is a
  separate stable decision with its own migration, not part of DEC-3; the
  implementation of DEC-3 adds PowerSearch to the family coverage check's
  pending list, where it stays until that decision or an amendment of the
  family record resolves which rule governs a composition that consumes
  member behavior.
- Known gap against `spec:AST-086/FR14`, a present-tense implementation gap
  note as this record carries where the shipped PowerSearch does not yet meet
  a requirement: FR19 routes the closed field's result count, and AR6 Clear all's
  after-close message, to the modal that holds the field. On the shipped
  `useAnnounce` those messages write only to the page-body regions, so a
  PowerSearch inside an open Dialog or modal Drawer does not yet meet that
  route; the AST-086 record lists the same gap for every owner that announces
  through the shared hook, and owns its closing: `useAnnounce` delivering
  inside the open Astryx modal that encloses its caller closes it for every
  owner at once, PowerSearch's calls unchanged.
- Should `date_absolute` with `isDateOnly: false` get a date-and-time editor in
  both presentations? Today both offer a date-only editor.
- Should Clear all leave read-only filters in place in both presentations? Today
  both clear every filter.
- The editor geometry contract (DEC-1, DEC-2) is accepted and current; its
  implementation and focused real-Chromium verification remain pending.
