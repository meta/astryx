# PowerSearch component contract

## Intent

PowerSearch provides structured filtering through field, operator, and value
selection. Its editor popover keeps the active editing task readable on both narrow
and wide search bars. When the editor can follow the PowerSearch width, it stays
aligned to that outer surface. When the 720 CSS px readability cap makes the editor
narrower, it stays near the stable control that opened it instead of stretching
across the page or depending on input modality.

PowerSearch also offers a touch presentation, the default on compact
coarse-pointer screens (DEC-3): the whole field becomes one trigger showing
display-only filter tokens, and the filter work moves into a stack of tall
modal bottom sheets — Filters, Add filter, and a value step, each opened above
the one that led to it and each dismissed back to it — that reads on a compact
touch screen without a software keyboard covering the editor. With a fine
pointer or on a screen that is not compact the field keeps the tokenizer and
editor popover, and `presentation="popover"` keeps them on every device. DEC-3 states the flow's shape.

Where the shipped PowerSearch does not yet meet a requirement, the row carries a
present-tense implementation gap note.

## Compatibility and migration

- Released default preserved: `no` for editor popovers anchored to a PowerSearch
  wider than 720 CSS px; other widths preserve their current sizing behavior.
- Compatibility class (DEC-1, DEC-2): intentional default layout and placement
  change with no public API change. DEC-3 adds the stable `presentation` prop
  and its `adaptive` default, as the two DEC-3 bullets below state.
- Controlled/uncontrolled behavior: unchanged.
- Calendar: date values follow the provider's calendar. A provider locale with a
  `-u-ca-` keyword keeps Gregorian dates (`spec:AST-111` DEC-2); set the
  provider's `calendar` to choose one.
- Migration decisions: `component:PowerSearch/DEC-1`,
  `component:PowerSearch/DEC-2`, and, for the `adaptive` default,
  `presentation="popover"` (below).
- Stable presentation (DEC-3): `presentation` is a new stable prop. The API
  change is additive: the prop is new and optional, and no existing prop,
  type, or export is removed or narrowed. The sheet presentation adds no
  theming target.
- Default change (DEC-3): `presentation` defaults to `adaptive`, a change of the released `popover` default. With a fine pointer, on a screen that is not compact, on the
  server, and while hydrating, a field without `presentation` renders the
  tokenizer field and editor popover exactly as before (`spec:AST-017/FR59`).
  On a compact coarse-pointer screen it renders the trigger and the sheet flow
  (FR11–FR21): filters are added and edited through stacked sheets, not the
  typeahead and editor popover, a filter commits when its value step
  confirms, and `menuWidth` and `tokenOverflowBehavior` have no surface. The behavior changes only there, which is what `adaptive` is for. `presentation="popover"` restores the previous surface
  on every device — the restoring input `spec:AST-017/DEC-23` and
  `architecture:public-component-api/INV16` name. No codemod adds it, because
  adding it to every PowerSearch would opt every caller out of the new
  default. The stable prop and this default ship together in a patch as `[feat]`: that release tier is a product decision of the engineering owner, with the agreement of the owner of `spec:AST-017` (DEC-3).
- One stable fix alongside DEC-3: the result count is not announced on mount under
  StrictMode (FR19). It qualifies as a `[fix]` under `spec:AST-017/FR5`: it
  restores the documented contract (only a change after mount is spoken), no
  `onChange` value, prop, or rendered text changes, and no valid consumer
  must change. It ships as a `[fix]` patch release of its own.
- A second stable fix: in the `popover`
  presentation, Backspace on an empty input removes no filter of a read-only
  field (FR22). It qualifies as a `[fix]` under `spec:AST-017/FR5`: it
  restores the documented `isReadOnly` contract, "Prevent adding, editing, or
  removing filters", no prop, `onChange` shape, or rendered text changes, and
  no valid consumer relies on a read-only field losing a filter. It ships as a
  `[fix]` patch release.
- A third stable fix: in the `popover`
  presentation, Clear all keeps read-only filters, reports `remove` at the
  first removed index, and shows only while an editable filter exists, and
  Backspace keeps a read-only filter (FR23). It is a `[fix]` (DEC-4): a
  read-only filter is non-removable by contract, so "all filters" in Clear
  all means every removable filter, and a Clear all that removes a read-only
  filter is a defect. `onChange` documents `index` as the affected position,
  which the first removed index is. It ships as a `[fix]` patch release.
- DEC-3 changes nothing in the `popover` presentation. Its Clear all is FR23's
  (DEC-4), which the sheet presentation's matches, and its dates are FR25's
  and FR26's (DEC-5, DEC-6), which the sheet presentation's match.
- One stable fix (DEC-5): a date-only
  `date_absolute` value reads as one day on the token, in the accessible
  label and announcements, and in the editor, in both presentations (FR25).
  What a caller observes: with `timezoneID` set, the token, the label, the
  exported `PowerSearchToken` and the editor show the day in `timezoneID`,
  and a day picked in an editor stores as that zone's midnight; with
  `timezoneID` unset, the stored day stays UTC midnight and the token, the
  label and `PowerSearchToken` show the UTC day with no time of day. A value
  whose operator sets `isDateOnly: false` is untouched. Ships as `[fix]`
  (`spec:AST-017` FR5, FR32): the shipped popover reads one date-only value
  in three zones (the token in the viewer's zone, the label in `timezoneID`
  with a time of day, the editor on the UTC day), so no consumer can validly
  rely on how a day is stored or read, and `timezoneID` is documented for
  date formatting, so honoring it restores that contract.
- One stable fix (DEC-6): a
  `date_absolute` operator with `isDateOnly: false` is an instant with a time
  of day in both presentations, and in the popover presentation it edits in
  a date picker beside a time field and its token shows the time (FR26). What
  a caller observes, only for an operator that sets `isDateOnly: false`: the
  popover's editor gains a time field; a value saved from
  it carries the time entered, in `timezoneID` else the viewer's zone, where
  it carried UTC midnight of the picked day; the token shows the date and
  time in that zone, where it showed the device's day alone. A
  `date_absolute` with `isDateOnly` unset or `true` is unchanged. Ships as a
  `[fix]` (`spec:AST-017` FR5, FR32): `isDateOnly` is documented as choosing a
  date picker without time only when true, and the shipped editor is the date
  picker for every value and stores midnight, so the option changes nothing
  and no consumer can validly rely on it; honoring it restores that contract.
- Refused dismissal (FR15c, `component:BottomSheet` DEC-5): while the discard
  confirmation is open, the Filters sheet, or the entry-point Add filter sheet,
  waits at its peek instead of springing back to its detent under the dialog.
  The dialog, its words, focus, and outcomes, the draft, Done, and `onChange`
  are unchanged, and no prop changes. It is a `[feat]`
  patch change (`spec:AST-017/FR7`, `/FR25`).

Consumer migration instructions belong in consumer docs and release notes.

## Ownership boundary

**Owns**

- The readable width range of the filter-editor popover.
- Identifying the stable control that opened the editor: the inner typeahead input
  for the add path, or the actual activated token/control for the edit path.
- Choosing which outer PowerSearch edge a width-capped editor aligns to from that
  opening control's geometry.
- Preserving the editing flow, content, and focus behavior while the editor's width
  and horizontal alignment change.
- The touch sheet presentation: its trigger, the Filters, Add filter, and value
  sheets, which of them are open at once and which one dismissing reveals,
  which control receives focus after each step, the staging of a value until
  the step confirms it, the `onChange` metadata of each commit, Clear all's
  confirmation, and which PowerSearch props the sheets honor.

**Does not own / non-goals**

- Main field/search-menu width — the existing `menuWidth` consumer surface is an
  exact pixel width forwarded to Tokenizer's main field menu, not a maximum and not
  an editor width control.
- General anchor positioning, viewport collision handling, top-layer hosting, or
  dismissal — owned by `architecture:layer-runtime`.
- Operator- and value-menu sizing inside the editor.
- A public prop for overriding editor width or placement.
- Pointer-coordinate placement, pointer-versus-keyboard branches, continuous
  pointer tracking, or an always-on geometry observer.
- The compact-touch resolution rule behind `adaptive`. PowerSearch resolves
  `adaptive` with the same shared policy the selection controls use
  (`component:Selector/FR4`); it adds no query of its own.
- The sheets' dialog, the one scrim of the stack of open modal sheets, gestures,
  snap behavior, keyboard accommodation, which sheet is on top and so takes a
  dismissal, how a covered sheet recedes, and how a dismissed top sheet reveals
  the sheet beneath it — owned by `component:BottomSheet` (its sheet stack) and
  `family:overlay-dismissal`.
- The list-value sheet a `string_list` or `entity_list` value opens inside the
  value step — owned by `component:Tokenizer` (its DEC-3 sheet presentation).

## Public concepts

One stable public concept is introduced: the `presentation` prop, with the
values `'popover' | 'bottom-sheet' | 'adaptive'` and `adaptive` the default,
typed by the exported `PowerSearchPresentation`, the value set the selection
controls and Tokenizer use (DEC-3).

The inclusive 400–720 CSS px range and conditional alignment of the editor
popover are internal PowerSearch readability policy, not callsite options.
Existing `menuWidth` remains an exact pixel width for only the main field/search
menu of the `popover` presentation.

In the sheet presentation the props that describe the tokenizer's typeahead
popover have no surface to act on: `menuWidth` and `tokenOverflowBehavior`.
Passing either while a field resolves to `bottom-sheet` warns once in
development and names `presentation="popover"`; neither is silently dropped. `ref` reaches the root element in
both presentations, the element this record promises
(`architecture:public-component-api/INV8`); `xstyle`, `className`, and `style`
reach the field container in both. `data-testid` reaches the field's primary
control: in the `popover` presentation the combobox input, where it is today,
and in the sheet presentation the trigger button. `handleRef.focusTypeahead()` and
`blurTypeahead()` act on the trigger. Every other prop keeps its meaning: `label` names the
trigger and `placeholder` is its empty text and the content-search placeholder;
`isDisabled`, `disabledMessage`, `startIcon`, `endContent`, `resultCount`,
`status`, `statusVariant`, `size`, `hasAutoFocus`, `onFocus`, and `onBlur`
apply to the trigger as FR11 states; `hasClear` governs Clear all (FR12);
`isReadOnly` governs the rows, Add filter, and the value step (FR12, FR13,
FR15); `maxSearchResults` and `maxOperatorMenuItems` apply to the Add filter
and value steps (FR13, FR17); `popoverSaveButtonLabel` and `components` apply
to the value step and the trigger (FR11, FR14); `maxTokenLength` applies to the
trigger's tokens as to the popover's (FR11). `timezoneID` names the zone the
sheet presentation reads and writes a date value in, on the trigger's tokens,
the Filters rows, and the date editors: a date-only value is its day there,
else the UTC day, and a value whose operator sets `isDateOnly: false` is its
date and time there, else in the viewer's zone (FR11, FR12, FR17).

## Behavioral and layout contract

Current requirements identify their basis and distinguish accepted contract from
implementation status. The contract is authoritative; the behavior remains unshipped
until its implementation and verification complete.

popover, rendered when `presentation` resolves to `popover`. The
editor popover does not render in the `bottom-sheet` presentation, whose surface
FR10–FR21 govern. FR25 governs a date-only value in both, and FR26 a date-and-time value.

### Allowed variation

- **AV1 — Viewport clamping.** The layer runtime may shift or shrink the editor
  when the preferred width or edge alignment would cross its viewport safe area.
- **AV2 — Writing direction.** Implementations may express the selected physical
  edge through logical alignment values as long as the rendered edge is correct in
  both LTR and RTL.
- **AV3 — Submenus.** Operator and value menus may retain their own width and
  collision behavior; this contract applies only to the filter-editor popover.
- **AV4 — Internal representation.** The shared opening-control descriptor may use
  refs, elements, or an equivalent package-internal value. Its observable geometry,
  lifetime, and precedence must satisfy FR3–FR9.
- **AV5 — Sheet flow composition.** The sheet presentation hosts its steps as
  standalone BottomSheets driven by one step state, each step's `isOpen` true
  while it is open or beneath an open step (FR15a), so the stack is
  `component:BottomSheet`'s own (FR5–FR9) and Filters opens as other sheets
  close only where FR15a names it; it may compose List, RadioList, TextInput,
  Calendar, Button, Heading, EmptyState and Text in any internal structure, and
  may load the whole surface on demand, provided FR10–FR21, AR4–AR6, and PR5
  hold and the composition stays within
  `architecture:component-style-authoring/INV7`: one presentation mounted per
  open layer, no content mounted twice, and, while one sheet of the flow is
  open, the open flow under a coarse pointer within the popover presentation's
  open editor under a fine pointer; each sheet open beneath the top one is the
  owner exception DEC-3 records with its counts, beyond the open-layer allowance
  (`spec:AST-017/FR60`, `DEC-29`). The Tokenizer's list-value sheet opens as one
  more sheet of the same stack above the step.
- **AV6 — Sheet layout.** Sheet padding, the field-list search threshold's
  visual placement, row density, and the footer's button widths may vary; the 44
  px minimum hit area of every sheet action (AR5) and the edge-to-edge Filters
  and field rows on the body's inset are the constants.

### Transformation and precedence order

- **ORD1 — Width.** Resolve outer PowerSearch width → apply the 400 px readable
  floor → apply the 720 px readable ceiling → yield to available viewport width.
- **ORD2 — Opening control.** Resolve the stable inner input or activated
  token/control for the current open.
- **ORD3 — Horizontal alignment.** If the ceiling did not narrow the editor, use
  outer logical start. Otherwise compare the opening control's physical edge gaps
  inside the outer PowerSearch → choose the nearer outer edge → use outer logical
  start on a tie.
- **ORD4 — Collision.** Let the layer runtime apply viewport collision handling
  after preferred width and edge selection.

### Performance and resources

- **PR1 — One batched open-time read.** PowerSearch MUST read the outer PowerSearch
  and opening-control geometry together once in response to open intent, never
  during React render.
- **PR2 — Hidden commit before show.** Placement state MUST commit while the editor
  popover is hidden, and the popover MUST show on the next animation frame. Real
  Chromium verification MUST prove there is no first-frame flash at a default or
  stale position.
- **PR3 — Latch, do not track.** The resolved opening control and preferred edge
  MUST remain latched until close. The implementation MUST NOT install continuous
  pointer tracking or an always-on geometry observer.
- **PR4 — CSS owns responsive geometry.** CSS anchor sizing and the layer runtime
  MUST own the 400–720 width policy and collision behavior. JavaScript may select
  the per-open anchor/alignment descriptor but MUST NOT continuously calculate
  popup width or collision offsets.
- **PR5 — The sheet surface is opt-in cost.** A field in the `popover`
  presentation does not load the sheet flow's code; the flow's chunk loads on
  demand while a field resolves to `bottom-sheet`, so the first press does not
  wait for the network, and renders nothing on the server or during the
  hydrating render. At rest the field renders none of the flow: its three
  dialogs, rows, search fields, editors and the Clear all confirmation are
  mounted only from the press until the exit has completed and focus is back
  on the trigger
  (`architecture:component-style-authoring/INV7`); the trigger, its end lane
  (the result count, `endContent`) and the field chrome of FR11 render as the
  field does.

## Accessibility contract

- **AR1 — Modality equivalence.** Pointer, keyboard, and programmatic activation of
  the same control MUST resolve the same preferred edge. Keyboard users retain the
  current field selection, editor focus, traversal, apply/cancel, Escape, and
  focus-return behavior.
- **AR2 — Semantic stability.** Width and placement MUST NOT change the current
  combobox, listbox, option, menu, or editor semantics and accessible names.
- **AR3 — Visible content.** Viewport clamping MUST keep all editor controls
  horizontally reachable without requiring page-level horizontal scrolling.
- **AR4 — Trigger semantics.** In the sheet presentation the trigger is a button
  named by the field label plus its visible text, with `aria-haspopup="dialog"`
  and `aria-expanded`; `status.message` and `disabledMessage` describe it; a
  disabled trigger uses `aria-disabled` and keeps its focus order; an
  interactive `endContent` is a sibling of the trigger with its own name and
  tab stop, never a descendant of it.
- **AR5 — Sheet semantics.** Each step is a modal dialog named by its title
  ("Filters", "Add filter", the value step's title), the open one on top of the
  sheets it was opened from, which are `inert` beneath it
  (`component:BottomSheet` FR6); the Filters rows, field rows, and suggestion
  rows are buttons named by their visible text, and a Filters row's trailing
  remove action is a button named "Remove {field label} filter" with that name
  as its tooltip; the Clear all confirmation is a modal `alertdialog` named
  "Clear all filters?" whose actions read "Clear filters" and "Keep filters",
  with Keep filters focused when it opens, so a stray Enter keeps the filters; a
  value choice is a radio in a `component:RadioList` (single choice) or a
  checkbox in a `component:CheckboxList` (`enum_list`), named by the field label
  (FR17); the operator step is a `component:RadioList` named "Operator"; the
  content search is a searchbox named "Search" controlling the suggestion list;
  the field-list search is a textbox named "Search filters"; every sheet action
  except the choice lists has a hit area at least 44 px tall, and the trailing
  remove action and the header's Add filter keep their medium visible size,
  their hit area meeting that minimum. The choice lists — the operator and
  value RadioList and CheckboxList — follow the standard list density and its
  shared touch band instead, as they do everywhere else (owner decision,
  cixzhang, 2026-11-07).
- **AR6 — Announcements and focus.** While a sheet is open, every announcement
  the flow makes — `Added {label}` for a committed suggestion or an
  `empty`-valued field row, `Removed {label}` for a filter removed by its row's
  trailing remove action, by a tap on an `empty`-valued filter's row, or by a
  caller's `Editor` override that calls `onSave(null)` while editing (FR14) (the
  label is the Filters row's text — the same "{label} {value}" catalog message
  the row renders, its summaries and relative-date values resolved from the
  catalog as FR12 states; the popover presentation's removal is the Tokenizer's
  `tokenRemoved` with the filter's `formatFilterValue` label, "{field}:
  {operator} {value}" — not the token's text: `1500` with `units: 'ms'` shows
  "1500" on the token and is announced "1,500 ms" — and the sheet's is the
  Filters row's text, so the two readings differ wherever FR12's row and
  `formatFilterValue` differ), the result count of FR19, the Add filter sheet's
  empty-result messages ("No results found", "No filters match your search"),
  each a compact EmptyState (FR13), and the value step's "This filter is no
  longer available" (FR14), plain rendered text, each read from its rendered
  element and spoken once per query that matches nothing, or once per opened
  filter, by the shared own-content module
  (`architecture:react-component-runtime/INV10`), and only while the message's
  sheet is the open one — a sheet beneath another, or one closed with its body
  retained, speaks nothing (FR18) — so nothing speaks them a second time, and
  reopening the same stale filter speaks its message again — is delivered by a
  persistent polite live region inside the open sheet: an element that stays
  mounted while its text changes and never mounts already holding the text to
  announce (`spec:AST-086/FR3`), that delivers the content added inside it at
  its own polite urgency (`spec:AST-086/FR4`), and that is the route an owner
  inside an open native modal takes (`spec:AST-086/FR14`), so the announcement
  reaches assistive technology behind the native modal dialog where a channel
  outside it does not. Clear all announces "Editable filters removed" while a
  read-only filter remains, otherwise "All filters removed", inside the Filters
  sheet once its confirmation dialog has closed — not before, since the
  confirmation is the top modal until then and hides the sheet's region. The
  result count follows the applied filters, which change on Done (FR15b), so
  no count changes with an edit inside the flow; after Done, while the flow is
  closed, the changed count takes the route `spec:AST-086/FR14` names for the
  field's position (FR19). Focus moves as FR16 states and returns
  to the trigger after the flow closes.

### `spec:AST-013` FR12 exception — calendars that need `Temporal`

- **Capability:** date values that PowerSearch (its tokens in both
  presentations, and the sheet's Filters rows and removal announcement) and
  PowerSearchToken write in the provider's calendar (`spec:AST-111` FR18), for
  calendars other than the Gregorian, Buddhist, Minguo, and Japanese calendars,
  which need the runtime's `Temporal`.
- **Reduction:** where `Temporal` is missing or does not support the calendar,
  as in Safari on macOS and iOS, such a calendar resolves to `gregory` before
  the first render and warns once in development, on the server and in the
  browser, naming `temporal-polyfill/full/global` (`spec:AST-111` FR5). Date
  values then show Gregorian dates; filter values stay Unix seconds. An
  application that loads a `Temporal` polyfill gets the full calendar. A
  server without `Temporal` renders Gregorian text, which a browser with
  `Temporal` does not match, so a server-rendered application loads `Temporal`
  on the server too.
- **Preserved obligations:** `spec:AST-013` FR7 and FR8, and FR9 whenever the
  server and the browser resolve the calendar the same way, outside the case of
  the Chinese and Dangi calendars in `spec:AST-111` FR19. The filter flow and
  the filter values do not change; nothing throws.
- **Evidence:** `PowerSearch.calendarSystems.test.tsx` with a `Temporal`
  polyfill and with `Temporal` removed; `PowerSearchBottomSheet.test.tsx`
  ("writes the trigger token and the Filters row in the provider calendar").
  Evidence gap: no real-browser run, and no server render and hydration test,
  under a calendar that needs `Temporal`.
- **Owner:** `nynexman4464`.
- **Review condition:** Safari ships `Temporal`.

## Decision log

### DEC-1 — PowerSearch owns one internal readable editor width

**Reference:** `component:PowerSearch/DEC-1`
**Decider:** `cixzhang`, 2026-08-31

A very wide editor makes a small field/operator/value task harder to scan, while a
callsite width prop would turn readability policy into permanent public API and
produce inconsistent products. PowerSearch therefore owns one internal preferred
range: outer PowerSearch width clamped to 400–720 CSS px, then constrained by the
viewport. This rule does not change Tokenizer's main-menu sizing or PowerSearch's
existing exact-pixel `menuWidth` surface.

Rejected: a public editor width/max-width prop, applying the 720 cap to Tokenizer's
main menu, or treating `menuWidth` as an editor width.

### DEC-2 — Only a capped editor follows the stable opening control

**Reference:** `component:PowerSearch/DEC-2`
**Decider:** `cixzhang`, 2026-08-31

A full-width or floor-expanded editor remains aligned to the outer PowerSearch.
Only when the 720 px ceiling makes the editor narrower does PowerSearch use the
stable opening control to choose the nearer outer edge. The add path uses the
inner typeahead input; the edit path uses the actual activated token/control. The
control's geometry produces the same result for pointer, keyboard, and programmatic
activation, and the result is latched until close.

Rejected: pointer-coordinate placement, pointer-versus-keyboard branches, always
using one edge, anchoring every width to the inner control, continuous tracking,
render-time geometry reads, and showing before hidden placement state commits.

### DEC-3 — The touch sheet is a stable presentation, and adaptive is the default

**Reference:** `component:PowerSearch/DEC-3`
**Decider:** `imdreamrunner`, 2026-11-03

PowerSearch offers its touch surface through a stable `presentation` prop,
with the values `popover`, `bottom-sheet`, and `adaptive` that the selection
controls and Tokenizer use, and `adaptive` is the default: the sheet flow on a
compact coarse-pointer screen, where the editor popover competes with the
software keyboard, and the tokenizer field with its editor popover everywhere
else. A caller's explicit value wins on every device, and `popover` keeps the
tokenizer field and editor popover (`architecture:public-component-api`
INV16). `adaptive` resolves through the shared compact coarse-pointer policy,
so a PowerSearch, a Tokenizer, and a Selector on the same page switch
together. The stable prop and the `adaptive` default ship together
in a patch release: the API change is additive, the behavior changes only on
compact coarse-pointer screens, and `presentation="popover"` keeps the
previous behavior everywhere. That release tier is the engineering owner's
product decision, made with the agreement of `cixzhang`, an owner of
`spec:AST-017`. Rejected: keeping `popover` as the default, because a
phone then gets the editor popover under the software keyboard unless the
caller opts in (`component:Selector` DEC-1 rejects the same default for the
same reason).

The sheet surface: the whole field is one trigger
with display-only tokens; a Filters sheet lists the filters as rows with
trailing remove actions, under a fixed header with Add filter and over a fixed
footer with Done and Clear all, and is one centered Add filter when empty; Add
filter opens above Filters and lists the fields, or carries the content search
with inline suggestions, its search unfocused until tapped; the value step opens
above the sheet that led to it, stages operator → value with the editor on the
sheet's surface, and confirms from its footer. Every step stays open beneath the
next, so a dismissal reveals the previous step and no sheet needs a Back action.
Closed vocabularies are rows; list values edit through the Tokenizer's sheet
presentation titled with the field label; a `nested` value uses the popover
presentation's built-in nested editor; a date-only value edits on an inline
Calendar in `timezoneID`, else UTC, and a value with a time of day on a
date-and-time control in `timezoneID`, else the viewer's zone; every other value
type uses the editor the popover presentation uses. Clear all asks for
confirmation, removes the filters the person can edit, keeps read-only ones, and
leaves Filters open. The flow edits a draft that Done applies, and a dismissal
with a changed draft asks before discarding it (FR15b, FR15c, DEC-7). Seven
details the flow fixes: a date-only value with no
`timezoneID` is its UTC day; a field whose every operator is `nested` lists,

### DEC-4 — Clear all keeps read-only filters

**Reference:** `component:PowerSearch/DEC-4`
**Decider:** `imdreamrunner`, 2026-11-02

A read-only filter is non-removable by contract: it has no remove control, and
no key or bulk action removes it either. "All filters" in Clear all therefore
means every removable filter, and a Clear all that removes a read-only filter
is a defect. Clear all removes the editable filters, keeps the read-only ones,
and reports `remove` at the first removed index — at once in the popover
presentation, on Done in the sheet presentation (FR15b). Backspace on an empty input
removes nothing when the last filter is read-only (FR23). Rejected: a Clear all
that also removes read-only filters (a filter the person cannot remove alone
would go with the rest).

### DEC-5 — A date-only value is one day in one zone

**Reference:** `component:PowerSearch/DEC-5`
**Decider:** `imdreamrunner`, 2026-11-02

A `date_absolute` value whose operator has `isDateOnly` unset or `true`, and
each absolute part of a `date_range`, is a calendar day. `timezoneID`, when set,
is the one zone the day is read and written in: the token's text, the
accessible label, the announcements, the sheet's rows, and the editors of both
presentations show the day the instant falls on there, and a day picked in an
editor stores as that zone's midnight. With no `timezoneID` the day is the UTC
day, read and written, so a value a caller stored as UTC midnight keeps its day
and its instant whatever the device's zone. Rejected: keeping the token on the
device's zone (a UTC-midnight day reads as the day before everywhere west of
UTC, and the editor then opens on a different day than the token shows, so
re-picking the token's day moves the value a day earlier each time). Rejected:
the viewer's zone as the fallback for a date-only value (a stored UTC-midnight
day would then be shown and, on edit, rewritten as a different instant on every
device west of UTC; the UTC fallback changes no stored value). Rejected: a
separate prop for the editor's zone (one field, one zone; `timezoneID` already
names it).

### DEC-6 — `isDateOnly: false` is an instant with a time of day

**Reference:** `component:PowerSearch/DEC-6`
**Decider:** `imdreamrunner`, 2026-11-02

A `date_absolute` operator that sets `isDateOnly: false` names a value with a
time of day. Its popover editor is a date picker beside a time field (the
sheet's control is FR17's), and its token shows the date and the time, both
reading and writing the instant in
`timezoneID` when the prop is set, else the viewer's zone: an instant has no
day of its own to keep stable, and the person reads it where they are; a field
that needs every viewer to see one wall-clock time passes `timezoneID`. An
operator with `isDateOnly` unset or `true` keeps the date picker. Rejected: a
date-only editor for `isDateOnly: false` (the option's one documented meaning
is a value with a time, and a date-only editor stored midnight and showed no
time, so the option changed nothing). Rejected: UTC as the fallback zone for an
instant (a wall-clock time typed by the person would then name a different
hour than the one they read on their clock). Rejected: a time on the token for
every `date_absolute` value (a calendar day has no time to show).

### DEC-7 — The sheet edits a draft that Done applies, and asks before discarding a changed one

**Reference:** `component:PowerSearch/DEC-7`
**Decider:** `imdreamrunner`, 2026-11-04, with the designer's confirmation

The sheet presentation holds a draft of the filter list from open: adding,
editing and removing a filter, and Clear all, change the draft, and the field's
`onChange` is called only when Done applies it (FR15b). A dismissal with a
changed draft asks before discarding it, through the confirmation Tokenizer's
sheet uses (FR15c). The save model is the one `component:Tokenizer` DEC-4
states for its sheet, so the two sheets a PowerSearch flow stacks — the filter
list and a list value's Tokenizer — commit the same way: with an explicit
action, never under the finger. Done reports the draft through the public
`onChange(filters, changeType, index)` by replaying the recorded edits in
order onto the field's latest `filters`, each call carrying the list after that
edit: a consumer receives the calls a popover session makes, with real change
types and indexes; one that keeps only the last call's list ends on the applied
list, since every call carries the whole list; and a filter the parent added
while the flow was open — a read-only one above all — survives, since the
replay starts from the list that holds it. An edit or removal whose target the
parent removed meanwhile is skipped, with nothing reported for it. Rejected: one call for the whole draft (the public `changeType`
has no value for a batch, and inventing one is an API change; a consumer that
switches on the type would receive a type it does not know). Rejected: replaying
only the net edits (a consumer that logs or reacts per change would see an
edit history that never happened). Rejected: applying the draft on every
dismissal (a swipe or a scrim tap would then commit by accident, which is what
the confirmation exists to prevent). Rejected: showing a controlled parent's
`filters` change inside the open flow (the draft is the flow's own list; the
change takes part on Done and shows on the next open). Rejected: replaying the
draft's own lists as recorded (a filter the parent added while the flow was
open would be replaced on Done).

## Open questions

- Known gap, pre-existing in the popover presentation, against
  `architecture:internationalization/INV1a`: its token writes the list,
  date-range, and nested summaries ("{n} items", "date range", "{n} filters") as
  English literals, joins the items of a list value with a literal ", " where
  FR12's rows use the locale's list format, and shows a relative-date value as
  the stored key (`3d_ago`), and its relative-date editor writes the choice
  labels ("3 days ago") as English literals. `formatFilterValue` resolves its
  summaries from the catalog but differs from the token in four places: it
  says "{n} entities" for an
  entity list where the token says "{n} items"; it formats an `integer` or
  `float` through the locale's number format and appends the operator's `units`
  where the token prints the raw number; it collapses a list to a count when the
  joined text exceeds the width budget, where the token compares the labels'
  total length, so the two collapse at different lengths; and it cuts a single
  value at a different length and with a different mark — the token's budget is
  `maxTokenLength` less the field and operator label lengths, at least 10, with
  3 characters of slack and "..." (three periods), where `formatFilterValue`
  cuts at `maxTokenLength` with "…" (the ellipsis character) — (both show a
  relative-date value as stored). The sheet presentation resolves all of these
  from the catalog, or the locale's formats, on its own surfaces (FR12, FR20)
  and shows the popover token's text on the trigger, except a date, which FR11
  reads in `timezoneID` or its fallback zone; changing the token's and the
  editor's own text is a separate stable change for the owner.
- Known gap against `family:input-fields/FR10`, opened by DEC-3: the sheet
  presentation's trigger composes Field for the box the tokenizer field has,
  so PowerSearch is a component that composes Field, which FR10 binds
  even outside the family's membership, and this record departs from FR10 in
  two places. Item 1: `ref`, `id`, `data-*`, `aria-*`, `hidden`, `inert`,
  `dir`, and DOM event handlers go to the primary semantic control under
  FR10, while this record keeps `ref` on the root in both presentations (the
  INV8 promise above), routes only `data-testid` to the primary control, and
  forwards no `id`, `aria-*`, other `data-*`, `hidden`, `inert`, `dir`, or
  handler at all — the stable component destructures its props with no rest.
  Items 2–4: PowerSearch's stable props carry root `xstyle`, `className`, and
  `style`, which both presentations apply to the field box — FR10's
  `container*` target — so the styling lands where FR10 puts it, but the
  props type still accepts the root names and offers no `container*` or
  `control*` parts. Moving `ref` or removing the root names is a stable API
  change for existing callers (`spec:AST-017/FR5`), so the conversion is a
  separate stable decision with its own migration, not part of DEC-3; the
  implementation of DEC-3 adds PowerSearch to the family coverage check's
  pending list, where it stays until that decision or an amendment of the
  family record resolves which rule governs a composition that consumes
  member behavior.
